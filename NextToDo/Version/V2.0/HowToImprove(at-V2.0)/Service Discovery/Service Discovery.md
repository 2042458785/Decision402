# 找服务：现状与改进计划

[English](<Service Discovery.en.md>)

## 现在怎么做

| 环节 | 现在的做法 |
|---|---|
| 理解任务 | DeepSeek 调用 `find_services`；目前只接受东京天气请求。 |
| 找商家 | 后端使用写在 `app.go` 中的本地 A/B/C/D，没有搜索真实商家；四家都返回固定的“东京 23°C”。 |
| 看报价 | 模拟模式使用假报价；预览和付款模式向本地接口发送 GET，读取 HTTP 402；目前只接受一个付款选项。 |
| 选商家 | Go 代码核对报价、查收款地址风险，再按预算和价格／风险偏好排序；模型不能指定收款人。 |

代码：[商家名单与查找](<../../../../../internal/agent/app.go>) · [模型工具](<../../../../../internal/agent/model.go>) · [报价检查](<../../../../../internal/agent/payment.go>)

## 现在的问题

| 问题 | 具体表现 |
|---|---|
| 没有真实数据 | 四家都给固定样例，不能回答真实的天气问题。 |
| 只认东京天气 | 其他地点或服务类型无法查找。 |
| 商家写死在代码里 | 加一家就要改代码，也没有保存服务类型和请求参数。 |
| 报价兼容性有限 | 只用 GET 读取报价，且只接受一个付款选项；一些真实商家要求 POST，或提供多种付款方式。 |

## 预计要加的点

| 要做什么 | 怎么做 | 做到什么算完成 |
|---|---|---|
| 接入第一家真实商家 | 选一个具体任务，核对接口、参数、HTTP 402 报价和当前 Base Sepolia 测试 USDC；小额试买。天气可先用于验证付款流程。 | 付完拿到真实数据，且地点、时间和必需字段正确；只拿到 402 不算完成。 |
| 建自己的服务列表 | 记录商家、服务类型、接口地址、GET／POST、参数和支持的付款方式。 | 后端能从列表读取商家；付款仍以当次 402 报价为准。 |
| 按任务找服务 | 模型识别用户要什么，后端从已接入的列表里找匹配接口。 | 没找到就明确回复“暂不支持”，不编造商家、不付款。 |
| 兼容真实报价 | 支持接口需要的 GET／POST；多个付款选项中只选符合当前链、USDC 和预算的一项，签名前再核对。 | 链、币种、金额或收款地址不符时停止。 |
| 增加同类商家 | 第一家跑通后，再接第二家提供同类数据的商家。 | 两家都交付可比较的数据，再按现有价格／风险规则选。 |
| 用目录找候选 | 可从 [Circle 服务目录](https://developers.circle.com/agent-stack/agent-marketplace/discovery-api)找线索，再逐家核对。 | 被目录收录不等于我们的钱包能付款，也不等于数据可用。 |
