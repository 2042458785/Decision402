# 钱包改进：第一、二阶段

[English](Wallet.en.md) · 2026-10-05

## 第一阶段：加密本地密钥

| 功能 | 原来怎样 | 改了什么 | 为什么改 | 实际用处 |
|---|---|---|---|---|
| 钱包私钥 | Agent 的明文私钥在 `.key` 文件里；文件虽限 `0600`，拿到内容仍可控制钱包。 | 用用户口令生成 go-ethereum 加密 keystore，保存在 Agent 文件中；口令不写盘。 | 文件权限挡不住文件内容被复制。 | 备份或搬走 Agent 文件时，别人不能仅凭文件直接花钱包里的钱。 |
| DeepSeek Key | 个人 Key 明文写进 Agent 的 `.json`；共用 Key 可从 `.env` 读。 | 个人 Key 用口令加密；共用 Key 只从进程环境变量 `DEEPSEEK_API_KEY` 读取。 | Agent 文件和配置文件可能被复制。 | 迁移 Agent 文件时不会顺带带走明文模型 Key。旧 `.env` 中的值需自己删除。 |
| 锁定／解锁 | 登录后没有单独的 Agent 钱包锁。 | 新钱包默认锁定；输入口令后，当前登录会话最多解锁 10 分钟。手动锁定、退出、到期或重启后要重新解锁。 | 登录状态不应一直等于签名权限。 | 做完任务可以立刻停掉新签名；别人拿到未解锁的页面也不能直接付款。 |
| 签名时用密钥 | 后台从明文文件读取私钥交给付款程序。 | 报价、预算和风险检查通过后，签名时短暂解密；用完尽力清理内存。 | 缩短私钥以明文出现在内存中的时间。 | 保留自动付款，同时减少密钥长期暴露的机会。 |
| 备份／恢复 | 没有供用户操作的加密备份与恢复流程。 | 输入口令下载加密 keystore；用文件和原口令恢复相同地址，测试覆盖恢复后签名。 | 换电脑或重装时不能靠复制明文私钥。 | 原钱包地址可以继续用；备份不含模型 Key，恢复时要重新填写。 |
| 已有钱包 | 更新代码不会自动改掉旧 `.key`。 | 点 `Encrypt old wallet` 设置口令；验证加密文件可解开后，替换原记录并删除原位置的 `.key`。 | 避免迁移失败导致旧钱包无法使用。 | 原地址和个人模型 Key 保留；此前另外复制的明文备份需自行处理。 |
| 页面、接口和日志 | 原接口已只返回公开钱包信息，但本地 JSON 有明文 Key，模型回复也缺少针对 Key 回显的拦截。 | 口令／Key 输入框遮挡并在操作后清空；普通接口和日志不输出明文密钥；模型回复若包含配置的 API Key 就丢弃。 | 防止常见的意外展示。 | 展示任务结果、排查问题时，减少配置的 Key 被带出来的机会。 |

## 第二阶段：用户控制付款

| 功能 | 第一阶段之后怎样 | 改了什么 | 为什么改 | 实际用处 |
|---|---|---|---|---|
| 钱包主控权 | 旧 Agent 是普通钱包；即使私钥已加密，后台解锁后仍可用完整私钥签名。MetaMask 负责登录和充值，不能撤销 Agent 的私钥。 | 新 Agent 使用 ERC-1271 智能钱包：MetaMask 控制合约，后台只保存加密的受限签名钥匙。 | 限制后台解锁后能做的事。 | 即使受限钥匙泄露，也不能绕过合约直接提走智能钱包的 USDC。 |
| 授权范围 | 只有应用检查每个任务的预算和风险；链上没有用户给 Agent 的收款白名单与期限。 | 用户用 MetaMask 发授权交易，写入收款白名单、单笔／每日额度和有效期。首次部署是另一笔交易。 | 把花钱边界交给钱包合约检查。 | 用户设好范围后，Agent 可在范围内自动买数据，不用每笔都找人签。 |
| 跨任务额度 | 每个任务检查自己的额度，多个任务不会合起来算每日花费。 | 每笔付款先在链上占用额度；同一个智能钱包的任务共用当天额度，重新授权也不会清零。 | 防止拆成多个任务后超支。 | 例如日限额 0.20 USDC，已有两笔各占 0.10，第三笔会被拒绝。 |
| 付款签名 | 本地检查通过后，普通钱包直接签 x402 付款。 | 链上先记录这笔付款的金额、收款人等信息，再由受限钥匙签名；合约只认已占额度的那笔签名。 | 防止只靠后台规则约束受限钥匙。 | 后台即使出错，也不能让该钥匙给白名单外地址签出有效付款。每笔多一笔链上交易。 |
| 撤销 | 本地锁定只能阻止新签名，已签出的付款仍可能结算。 | 用户用 MetaMask 发 `Revoke onchain`；交易上链后，旧授权下尚未结算的签名失效。 | 用户需要从链上收回授权。 | 发现异常时可以停掉后续付款；已经完成的转账无法撤回。 |
| 转出／提现 | 页面没有把 Agent 余额转回用户的操作。 | `Withdraw with MetaMask` 只能由主控发起，USDC 只能转回主控地址。 | 停用 Agent 时不能把余额困在钱包里。 | 用户结束试用后可取回剩余测试 USDC；受限钥匙不能提现。 |
| 后台停机 | 撤销和提现若只靠项目页面，后台故障时会影响用户操作。 | 可保存独立控制页 `wallet-control.html` 和合约地址，用 MetaMask 直接撤销、提现。 | 用户控制权不能依赖后台一直在线。 | 项目程序停了，仍能管理已部署的钱包。 |
| 备份含义 | 第一阶段的 keystore 备份的是旧普通钱包的完整私钥。 | 新智能钱包的 keystore 只备份受限钥匙；恢复后要重新绑定原合约地址。 | 两种钥匙的权限不同。 | 换电脑可继续使用 Agent；MetaMask 主控钱包要单独备份。 |
| 旧钱包 | 已加密的旧普通钱包仍有原地址和余额。 | 旧钱包保持原地址；想用智能钱包需新建并自行转入资金。 | 当前项目不会把旧地址转成新合约地址。 | 不会误把旧钱包显示成已经受链上规则保护。 |

## 现在怎么操作

| 场景 | 做法 |
|---|---|
| 新 Agent | MetaMask 准备 Base Sepolia 测试 ETH → `Create agent + session key` → `Deploy with MetaMask` → `Fund with MetaMask` 给合约充测试 USDC → `Fund session gas` 给受限钥匙地址充少量测试 ETH → `Authorize with MetaMask` 设置白名单、限额和有效期 → 解锁后运行任务。部署和授权是两笔交易；每笔购买还要上链占额度。 |
| 已有旧 Agent | 先点 `Encrypt old wallet` 完成第一阶段迁移。要用第二阶段功能，再创建智能钱包并自行转入资金。 |
| 换电脑 | 保存加密 keystore、口令及智能钱包合约地址。恢复时选对钱包类型；智能钱包还要绑定原合约地址。备份文件不含个人 DeepSeek Key。 |
| 暂停或退出 | `Lock now` 停止本地新签名；`Revoke onchain` 在交易上链后作废链上授权；`Withdraw with MetaMask` 把智能钱包余额转回自己。 |

## 仍需知道

| 情况 | 事实 |
|---|---|
| “永不泄露” | 口令和 Key 输入时会短暂经过页面与后台内存；Go 不能保证擦掉运行库的所有副本。不要把其他秘密写进任务文本，因为任务文本会保存。 |
| 每日额度和手续费 | 按 UTC 零点重置（北京时间 08:00）。付款未成功，已占的额度当天也不退；跨日后，前一天尚未结算的签名失效。受限钥匙地址可花自己的 ETH，只给它少量手续费。 |
| 付款结果不明 | 占额度的交易哈希先保存，USDC 付款签名前另记一笔。USDC 付款结果未知时，现有程序仍会挡住后续付款，避免重复付。部署超时也要先查交易，成功后绑定原合约，别重复部署。 |
| 能力范围 | 当前是 ERC-1271 智能钱包，没有实现完整 ERC-4337。旧普通钱包仍由后台保管加密私钥；新钱包的受限钥匙也保存在后台。 |
| 验证范围 | 已有合约、本地 x402 扣款、Go 并发和模拟 MetaMask 页面测试。尚未在公共 Base Sepolia 用真实 MetaMask 与公共 facilitator 跑完整付款，也未做独立合约审计。旧 `cmd/x402-demo` 的演示密钥未迁入 Agent 钱包。 |

## 怎么验证

| 阶段 | 已有检查 |
|---|---|
| 第一阶段 | 错误口令、其他用户或会话不能解锁；备份恢复后地址不变且能签名；迁移中断可继续；签名前锁定不能付款。见 [`vault_test.go`](../../../../../internal/agent/vault_test.go)。 |
