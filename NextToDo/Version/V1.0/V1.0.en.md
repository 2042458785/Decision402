# Decision402 V1.0 — ETHGlobalTokyo2026 Hackathon Version

Recorded: 2026-10-03. [中文](V1.0)

This document describes the current business flow, excluding planned improvements. It covers the web agent started by `cmd/decision402`; the standalone CLI demos are separate.

- Code baseline: [`403638b`](https://github.com/2042458785/Decision402/commit/403638be173ee99f633d332948b5cf882360ec5c). HEAD was `3a3c31c` when reviewed; it only added planning documents, with no business-code changes from the baseline.
- Runtime: a local Go server and Vue UI. Payments use Base Sepolia test USDC only.
- Current use case: choose one of four local paid endpoints to buy a fixed Tokyo 23°C weather sample. This is neither live weather nor a public service marketplace.
- Checked against source code; no live API calls or testnet payments were rerun for this document. `V1.0` is a version name, not a production-readiness claim.

## Flow at a glance

**Connect wallet → create agent → fund with test tokens → set task and rules → fetch quotes → screen addresses → select by policy → preview or pay → show records.**

## Execution order

1. **Connect the wallet.** The UI connects MetaMask, switches to Base Sepolia, and asks the user to sign a login message. The server verifies it and opens a session. Login does not transfer funds.
2. **Create an agent.** The user enters a name and DeepSeek settings. The server generates a separate agent wallet and associates it with the signed-in owner. Its private key and any personal model API key stay in local files with `0600` permissions.
3. **Prepare payment funds.** The user transfers test USDC to the agent wallet through MetaMask. Only `pay` needs payment funds; simulation and preview do not transfer tokens.
4. **Submit a task.** The user sets the instruction, mode, per-payment limit, task limit, and selection preference. The server validates ownership and parameters, then saves and runs the task. The same task ID and payload return the original task; changing the payload under that ID is rejected.
5. **Call tools through the model.** DeepSeek interprets the instruction and calls `find_services`, then `execute_purchase`. The tools currently support only the Tokyo sample. Go code selects and pays; the model cannot override recipients or budgets.
6. **Fetch quotes and screen risk.** The server examines A/B/C/D. Live modes fetch HTTP 402 quotes from local endpoints, validate the chain, token, amount, recipient, and authorization fields, then call Intercepta for the quoted recipient. Matching addresses share one scan during discovery.
7. **Filter and rank.** Exclude invalid quotes, unknown or high risk, and candidates outside the user's risk or budget limits. Price preference sorts by price, then risk; risk preference sorts by risk, then price. Stop if no candidate qualifies.
8. **Execute the selected mode.** Simulation and preview finish with the selection result. Payment mode requests the chosen endpoint again. Before signing, it checks that the quote is unchanged, rescans the recipient, and checks policy. It writes a payment-attempt reservation to disk before the agent wallet signs the x402 authorization. The seller uses an external facilitator to verify and settle payment, then returns a response.
9. **Save and display.** The application reads the `PAYMENT-RESPONSE` settlement header before checking the HTTP status and JSON body. It saves the task, selection reasons, payment outcome, and transaction hash. The UI polls for these records.

## Three modes

| Mode | Quotes and risk | Payment |
|---|---|---|
| `simulate` | Fixed simulated values: A/B risk 2, C risk 1, D risk 0 | No signing or payment |
| `preview` | Real HTTP 402 requests to local endpoints and real Intercepta calls | No signing or payment |
| `pay` | Same as preview, with another quote and risk check before signing | One testnet payment attempt |

All three modes call DeepSeek and may incur model charges. The UI requires an agent in every mode. It submits risk limit 0 for `preview`/`pay`; risk limit 1 is exposed only in simulation. Backend policy supports both 0 and 1.

## Four demo providers

| Provider | Price in test USDC | Recipient configuration |
|---|---|---|
| A | 0.005 | Risk fixture address |
| B | 0.02 | The same risk fixture address as A |
| C | 0.01 | Separate advisory-risk fixture; uses D's address if not configured |
| D | 0.05 | Expected-normal fixture address |

These risk labels describe configuration intent. Live decisions depend on API results and project rules. Levels 0/1/2 are defined by this project, not official Intercepta risk bands. No detected risk is not a safety guarantee.

## Failure handling

- **Failure before signing:** Stop, usually with `held` status. Do not automatically buy from another provider.
- **Signed, settlement unknown:** Mark `unknown`; do not retry automatically.
- **Successful settlement header, unreadable data:** Keep `settled` and attach a data error; do not pay again.
- **Reserved attempt without confirmed settlement:** Block new payments across the service until manually reconciled.
- **Server restart:** Change previously queued/running tasks to `held`; do not resume them automatically. Tasks run serially across the service.

## V1.0 limitations

- At most one payment attempt per task. Per-payment and task limits are each capped at 0.10 test USDC. There is no daily or cross-task spending ledger.
- Initial selection can avoid ineligible providers. Automatic switching after the selected provider fails and automatic payment reconciliation are not implemented.
- The application records settlement from response headers without independently checking the chain. Data checks cover status, size, and JSON format, not business quality.
- Local private keys are unencrypted. This is not ready for public multi-user custody, and Arc mainnet is not supported.
- Dependencies include DeepSeek, Intercepta, and the seller's `https://x402.org/facilitator`. Even simulation is not fully offline.
